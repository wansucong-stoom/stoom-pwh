# r29 편집 경로·문서 전송·Store 알림 검증

[문서 모음](../README.md) · [코어 변경](../RHWP-DIFFERENCES.md#inline-object-cursor-and-grouped-textbox) · [Desktop](../PWH-DESKTOP.md#store-update-notice)

Pwh 0.6.56 / Desktop 소스 0.1.37 / 공통 코어 r29의 검증 범위입니다. 기존 88개 패치에 89·90번을 순서대로 적용합니다. 문서명·쪽·표 번호에 따른 보정과 사용자 실문서 편집은 추가하지 않았습니다. GitHub 공개, MSIX 생성, Store 심사·게시는 별도 단계입니다.

## 원인과 적용 계층

| 현상 | 확인한 발생 계층·원인 | 수정과 범위 |
| --- | --- | --- |
| 표처럼 보이는 묶음 제목의 글에 커서가 들어가지 않음 | rhwp 기반 코어의 묶음 내부 글상자 해석 누락과 공통 Studio의 도형 이동 우선 처리 | 하나의 글상자만 있는 묶음에서 원본 이야기를 찾아 편집. 묶음을 선택한 뒤 안쪽 글을 다시 클릭하며 크기 조절 핸들은 우선 유지 |
| 글자처럼 취급한 표 앞뒤 커서·같은 줄 선택이 합쳐짐 | 공통 편집기가 원문 텍스트 오프셋으로 위치를 축약하고 개체의 앞뒤를 잃음 | 본문 최상위 TAC 표의 좌우 바깥 커서, Home/End·Shift·드래그와 개체 범위 복사·삭제·실행 취소 연결 |

조판부호 표시나 `[표]` 클릭 선택은 이번 변경에 포함하지 않습니다. 그림의 기존 커서·선택 경로를 표 커서 우회로 교체하지 않습니다.

## 코드와 격리 시험

최적화한 정식 r29 코어 전체 시험은 **600건 통과 / 실패 0건 / 선택적 제외 13건**입니다. 제외를 통과 수에 합산하지 않습니다. 독립 r13 비교 코어와 실제 패치 소스를 사용하는 검사를 포함합니다.

- [묶음 글상자](../../tests/grouped-textbox.test.mjs): 단일·더 깊은 단일 글상자의 적중·삽입·삭제·저장·재열기와 묶음 보존. 여러 글상자가 있는 두 구조의 잘못된 편집 거절.
- [본문 인라인 개체](../../tests/body-inline-range.test.mjs): 표 앞뒤 논리 위치, 줄 끝, 복사, 선택 삭제, 원래 조각 복원. 서식 있는 두 글자 사이에서 표만 삭제하고 글자와 굵기 보존.
- [전송량 선택](../../tests/document-transfer.test.mjs), [분할 저장](../../tests/chunk-save.test.mjs), [64MiB 초과 전송](../../tests/large-document-transfer.test.mjs): 크기·상한·오프셋·원본 변경·재시도·최종 SHA-256과 게시 경계.
- [Store 조회](../../tests/store-update-check.test.mjs)와 [호스트 연결](../../tests/store-update-host.test.mjs): 신원·버전·동시 조회·캐시·실패, 미리보기 채널·다른 Origin 거절, MSI 미실행.

65MiB 합성 데이터의 로컬 전송·저장 시험은 2MiB씩 **33회**, SHA-256 동일로 끝났습니다. 약 1.1초는 이 PC에서 측정한 한 번의 연결·저장 시험이며 실제 파일 조판·첫 화면을 포함하지 않습니다. 512KiB에서는 130회가 필요하므로 요청 수를 줄이는 효과는 있지만 처리 속도 4배를 의미하지 않습니다.

다운로드는 문서 전체를 매 청크마다 읽지 않고 파일 메타데이터·스트리밍 해시와 범위 읽기를 사용합니다. 브라우저가 지원하면 TypedArray의 네이티브 Base64 변환을 사용하고, 호환 경로도 바이트마다 콜백을 호출하는 변환을 피합니다. 저장 결과 전체 검증의 메모리 사용, 직렬 요청 왕복과 파싱·레이아웃 시간은 남습니다. 별도 WASM·글꼴·그림·AI 작업 제한은 유지합니다.

### 실제 브라우저에서 분리한 시간

약 65MiB **유효한 합성 HWPX 컨테이너**의 브라우저 열기 성능을 측정했습니다. 작은 표 본문에 참조하지 않는 비압축 시험 데이터를 넣어 파일 전송 크기만 늘린 자료이며 실제 고용량 복합 문서의 대용은 아닙니다. 두 조건 모두 같은 33회 전송이고, 바이트 변환 보완 전·후를 비교했습니다.

| 구간 | 변환 보완 전 | 보완 후 |
| --- | ---: | ---: |
| 첫 문서 청크 요청 → 마지막 응답 JSON 수신 | 11.08초 | 2.13초 |
| 탐색 시작 → 편집기 준비 | 19.71초 | 12.28초 |

전송 구간은 약 80.8%, 전체 준비 시간은 약 37.7% 줄었습니다. 같은 PC·브라우저의 한 번씩 측정이며 반복 통계나 모든 파일의 성능 보장은 아닙니다. 후자는 WASM 파싱·문서 조판·글꼴·첫 화면 준비를 포함합니다. 보완 후에도 문서 로드 호출 자체에 약 8.65초가 남아 전송 최적화만으로 없어지지 않습니다. [변환 회귀 시험](../../tests/base64-bytes.test.mjs)은 모든 바이트 값·부분 뷰·패딩·2MiB 청크·잘못된 인코딩을 독립적인 Buffer 결과와 대조합니다.

## 실제 입력과 Windows 조회의 구분

브라우저 입력 시험에서 `isTrusted=true` 키를 확인했습니다. 표 앞의 커서에서 Shift+End로 개체 전체가 선택되고 Ctrl+C·Delete·Ctrl+Z로 복사·삭제·복원이 이어집니다. 화면에서도 표 전체 강조와 글줄 높이의 커서를 확인했습니다. 합성 묶음은 실제 클릭으로 텍스트 편집에 들어가 타이핑·실행 취소·다시 실행 후 원문으로 복원했습니다.

TEST 4 사본의 실제 묶음 제목에서도 클릭으로 글자 위치에 들어가 입력 후 실행 취소했습니다. 해당 글자 수는 14 → 15 → 14로 복원됐고 78쪽을 유지했습니다. 원본에 저장하지 않았습니다. 이 동작을 [신뢰된 입력 회귀 시험](../../tests/inline-object-cursors-browser.test.mjs)으로도 보존합니다.

Windows에 설치된 정식 Store 패키지 신원으로 읽기 전용 조회를 실행해 현재 버전과 `current` 응답을 받았습니다. 설치 가능한 새 버전이 있는 상태의 상단 버튼은 주입한 시험 응답으로 표시·클릭 경로를 확인했습니다. 이것을 실제 Store 업데이트 다운로드·설치 성공으로 보고하지 않습니다.

Windows IME, 실제 프린터, 모든 묶음 도형, 실제 고용량 복합 문서의 편집 속도는 별도 범위입니다. 업데이트 알림이 없는 이전 설치판은 기능을 포함한 버전을 Store에서 먼저 받아야 합니다.

## 빌드·되돌리기

공통·Desktop 편집기와 각각의 manifest를 함께 생성합니다. 고정 소스·패치·WASM·바인딩·빌드 입력과 검증 기록을 런타임 잠금 파일로 묶으며 정확한 해시는 릴리스의 `BUILD-RECORD.json`, `runtime-lock.json`, `SHA256SUMS.txt`를 기준으로 합니다.

문제가 확인되면 문서를 저장·종료한 뒤 이전 0.6.55 플러그인과 r28 런타임을 한 쌍으로 사용합니다. editor.js나 WASM 하나만 서로 다른 버전으로 섞지 않으며 문서·프로필은 삭제하지 않습니다. Store판의 설치·업데이트는 Store 채널로 관리합니다.
