# 셀 그림 높이와 중복 자원 처리

상태: **후속 공통 코어·편집기 후보**. 설치판 0.1.41과 배포 런타임 r29를 교체했다는 뜻은 아닙니다. rhwp 0.8.7 기반 기존 90개 패치 뒤에 91~96번을 적용한 WASM과 같은 소스에서 만든 공통·Desktop 편집기를 검증했습니다.

## 변경 범위

| 계층 | 원인 | 변경 |
| --- | --- | --- |
| rhwp 기반 코어 | 그림 오프셋으로 셀 높이를 덮어써 원래 빈 공간을 축소 | 실제 소유 셀의 전체 경로를 사용하고 기존 셀·표 높이를 최소값으로 보존. 그림을 내릴 때 필요한 확장은 허용 |
| rhwp 기반 코어 | 일부 머리선만으로 사방의 표 테두리를 추정 | 기존 외곽선이 표 기본선의 종류·굵기·색과 일치할 때만 레거시 외곽선 복원 허용 |
| rhwp 기반 코어 | 빈 표 앵커의 저장된 글줄·간격과 실제 개체 높이를 중복 합산 | 저장된 프레임을 확인해 쪽 분할과 그리기에 같은 점유 높이를 전달. 중첩 셀의 빈 앵커도 개체와 글줄의 합집합 사용 |
| rhwp 기반 코어 | 레이어 조회마다 동일 내장 그림을 다시 압축 해제 | 불변 컨테이너 resolver와 원본 자원 키로 공유. 최대 64MiB·64항목, 문서 소유권과 호출별 읽기 상한 검사 |
| rhwp 기반 코어 | HWPX 저장마다 변하지 않은 내장 그림·차트를 다시 압축 | 전체 바이트의 SHA-256·길이·파일명이 같은 정규화된 ZIP 항목 재사용. 작업 스레드별 압축 바이트 최대 32MiB·64항목 |
| Pwh 공통 편집기 | 문서 지문·복구본의 반복 내보내기와 별도 형식의 중복 자동 저장 | 추적된 같은 리비전의 HWPX 내보내기 결과 재사용. 실제 복구 저장 완료 후에만 중복 경로 생략. 드래그 중 동기 내보내기 연기 |
| Pwh 공통 연결 | 같은 TTC 파일의 서로 다른 face를 동시에 반복 전송 | SHA-256과 파일 크기로 진행 중 전송 공유. face별 최신 식별자 검사·독립 버퍼·취소 처리 유지 |

캐시는 불변 바이트에만 적용합니다. 외부의 변경 가능한 resolver는 명시적으로 참여하지 않으면 원래 읽기를 유지합니다. 실패한 읽기는 저장하지 않으며 자원 교체·다른 문서에 이전 바이트를 대신 쓰지 않습니다. 원본 컨테이너를 캐시가 계속 소유하지 않습니다.

압축 캐시는 현재 읽은 전체 내용을 확인한 뒤 사용합니다. OLE 크기 접두어 복원과 자원 읽기 상한·손실 보고를 유지하고, 원본 ZIP 대신 기존 쓰기 방식이 생성한 항목만 병합합니다. 1KiB 미만·32MiB 초과 자원은 기존 경로를 사용하며 XML은 매번 생성합니다.

문서 지문 캐시는 표시·복구 경로에 한정합니다. 명시적 저장과 충돌 검증의 fresh 내보내기는 유지합니다. 복구 저장이 실패했거나 큰 문서 등으로 공통 복구 경로가 적용되지 않으면 기존 자동 저장을 사용합니다. 보호 문서의 복구 차단도 먼저 검사합니다.

## 검증

- 실제 수정 WASM을 지정한 공통 시험: **629 통과·0 실패·40 생략**, 144개 시험 파일. 생략된 외부 연동·네이티브 환경 시험은 통과에 포함하지 않습니다.
- 기존 5개 문서 **245쪽**: r29와 쪽 수·글자 좌표·인쇄 SVG 동일. 후보의 저장·재열기 결과도 동일합니다. 기존 150쪽 묶음과 17쪽 문서를 포함합니다.
- 추가 7쪽 기준 문서: 수정 전 9쪽에서 후보 7쪽으로 복원. 공통 코어의 print SVG를 실물 크기로 출력한 검토 PDF는 기준 PDF와 7쪽 각각의 정규화 추출 문자가 같습니다. 투명 선을 끈 실제 편집 화면에서 불필요한 표 외곽선 제거를 확인했습니다. Desktop 인쇄 대화상자나 모든 글꼴 환경의 픽셀 일치를 뜻하지 않습니다.
- 합성 평면·중첩 셀에서 확장 후 높이 보존, 병합 셀, 빈 앵커 앞 본문, 여러 세로 정렬, 쪽 경계, 실행 취소와 저장·재열기를 검사합니다. 실제 시험 사본의 마우스 이동 후 Ctrl+Z도 원래 표 높이·그림 위치를 복원합니다.
- 내장 자원 캐시의 실제 Rust 소스로 소유자 분리·공유 할당·상한·LRU·문서 해제·실패 후 재시도·변경 가능한 resolver를 검사합니다.
- 압축 캐시의 실제 Rust 소스로 키 구분·공유 할당·상한·LRU를 검사합니다. 실제 WASM에서 그림 교체, 같은 파일명의 다른 문서, 이동·실행 취소·재열기를 확인했습니다. 기준 코어와 후보의 17회 내보내기 바이트가 같으며 실행 순서를 반대로 바꾼 비교도 같았습니다.
- 같은 리비전의 복구본과 fresh 내보내기 SHA-256이 같고, 반환된 복구 버퍼를 수정해도 내부 보관본은 바뀌지 않습니다. 복구 실패 시 기존 경로, 드래그 연기, 보호 문서 우선 차단도 검사했습니다.
- 독립된 두 빌드의 공통·Desktop 출력 6개가 같고 엄격한 TypeScript 검사를 통과했습니다.

## 측정과 한계

같은 시험 사본의 도장을 6단계로 움직인 한 차례의 전후 비교입니다. 도중 네트워크 요청과 글꼴 재로딩은 두 경우 모두 0회였습니다.

| 동기 처리 합계 | 이전 후보 | 수정 후보 |
| --- | ---: | ---: |
| 이동 중 화면 그리기 18회 | 767.3ms | 658.3ms |
| 그림 레이어 트리 조회 42회 | 391.9ms | 250.3ms |
| 셀 그림 위치 변경 6회 | 39.5ms | 10.5ms |

위 표는 91~95번 후보의 측정이며 서로 포함되는 호출이므로 합산하지 않습니다. 백그라운드 화면의 프레임 제한과 실행 환경의 영향을 받으며 전체 드래그 지연·FPS·모든 문서의 개선율을 뜻하지 않습니다.

96번 압축 재사용을 추가한 뒤, 같은 문서의 WASM 내보내기만 순서를 바꿔 두 차례 비교했습니다. 각 차례에서 반복 저장 8회와 그림 이동 후 저장 8회의 중앙값을 구했습니다.

| 내보내기 측정 | 95번까지 | 96번 포함 |
| --- | ---: | ---: |
| 반복 저장 중앙값 | 179~180ms | 53~74ms |
| 그림 이동 후 저장 중앙값 | 179~191ms | 55~63ms |
| 캐시가 없는 첫 저장 | 238~300ms | 313~338ms |

반복 편집 저장은 약 65~69% 줄었으나 첫 저장은 해시 계산과 임시 항목 생성으로 39~75ms 늘었습니다. 이는 두 번의 순서 교대 측정이며 통계적 성능 보증은 아닙니다. 결과 HWPX의 크기와 전체 바이트는 유지됐습니다. 별도 실제 화면의 6단계 드래그에서는 이동 후 복구 내보내기 한 번이 69ms였으며, 앞선 후보의 별도 실행에서 측정한 509ms와 구분합니다. 두 실행에서 복구 완료·표 높이·Ctrl+Z 복원을 확인했습니다.

압축 재사용은 동기 코어 경로의 계산량을 줄이는 변경입니다. 내보내기를 작업 스레드로 옮긴 변경은 아니며, 첫 저장과 남은 약 60~70ms의 동기 처리는 남아 있습니다. 기존 드래그 중 내보내기 연기와 같은 리비전의 복구 결과 재사용을 함께 적용합니다.

별도 합성 글꼴 전송 시험에서는 2.5MiB TTC의 두 face 요청이 12회에서 7회로, 전달량이 약 5MiB에서 3MiB로 줄었습니다. 실제 문서 편집 시간과 구분합니다.

배포물의 큰 동일 파일은 주로 각 구성 요소의 라이선스·고지 사본이었습니다. 편집 중 읽는 자원이 아니므로 속도 개선을 이유로 삭제하지 않습니다. 화면 그리기·레이어 조회와 대용량 내보내기 비용은 남아 있으며 모든 지연이 해결됐다고 보지 않습니다.
